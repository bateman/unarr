# Audit 2 — HTTP behaviour outside the JSON bodies: Sonarr vs Unarr

Static, read-only. Nothing was compiled or run on either side.

**Paths.** Sonarr paths are relative to `<sonarr>/src/`; `Http/` = `Sonarr.Http/`, `Host/` = `NzbDrone.Host/`. Unarr paths are relative to `crates/`; `api/` = `unarr-api/src/`.

**Evidence labels.**
- Plain statements are read directly from the cited lines.
- **[fw]** = the Sonarr (or Unarr) side depends on ASP.NET Core / Kestrel / axum / tower-http default behaviour that is *not* in the repo; I state it from knowledge of the framework, not from code I read. Treat these as needing one live check.
- **UNSURE** = I could not decide from the code.

**Status column** starts with exactly one of: `SAME`, `DIFFERENT`, `MISSING`, `OUT OF SCOPE`, `UNSURE`.

Sonarr pipeline order, for reference (`Host/Startup.cs:244-283`): ForwardedHeaders → HostFiltering → LoggingMiddleware → UsePathBase(UrlBase) → ExceptionHandler → Routing → Cors → Authentication → Authorization → ResponseCompression → VersionMiddleware → UrlBaseMiddleware → StartingUpMiddleware → CacheHeaderMiddleware → IfModifiedMiddleware → BufferingMiddleware(`/api/v3/command`) → WebSockets → [Swagger, debug only] → endpoints (`/signalr/messages` hub with policy `SignalR`, controllers).

Unarr order (`api/lib.rs:195-292`): `require_allowed_host` → `lowercase_api_path` → `put_resource_id` → [nest under URL base] → TraceLayer → three merged routers: API (`version_header` layer; `require_api_key` + `reject_put_without_id` as route layers), `open` (favicon, Content, login, logout, SignalR), `pages` (everything else, behind `ui::require_ui_auth`).

## Summary

89 behaviours compared: **SAME 28 · DIFFERENT 35 · MISSING 21 · OUT OF SCOPE 3 · UNSURE 2**.
Of the 56 DIFFERENT/MISSING: **high 3 · medium 14 · low 39**.

High
- 2.1 `/ping` missing (answers `index.html`, a login redirect or a Basic challenge instead of anonymous JSON).
- 2.2 `/feed/v3/calendar/sonarr.ics` missing (404).
- 2.4 `/api/v3/mediacover/{id}/{file}` missing (404): no way to load a cover with the API key.

Medium
- 1.3 `X-Forwarded-Host` not applied before the allowed-hosts check.
- 1.8 No `Auth-Failure` / `Auth-Success` log lines.
- 1.10 Request outside the URL base: 404 instead of a 307 into it.
- 1.16 Trailing slash is a different route (404, or `index.html` for `/login/`).
- 1.17 No CORS headers or preflight on the API.
- 1.23 `/initialize.json` (API key) sent without `no-store`.
- 1.24 `/api`, `/api/v1/…` and other non-v3 API paths answer `index.html` 200 instead of 401/404.
- 1.29 2 MiB request-body limit where Sonarr has none.
- 2.11 SignalR advertises SSE and long polling but implements only WebSockets.
- 3.2 `Authorization: Bearer <apikey>` not accepted (API and SignalR).
- 3.4 Session cookie never `Secure`; `Path=/base/` instead of `/base`.
- 3.6 Session is 1 day / 7 days fixed instead of 7 days sliding.
- 3.15 `TrustCgnatIpAddresses` is stored but never used.
- 4.5 `manifest.json` served with literal `__INSTANCE_NAME__` / `__URL_BASE__`.

Rows marked **[fw]** rest on framework defaults I did not read in either repository; the ones that carry a medium rating on that basis alone are 1.16 (trailing slash), 1.24/1.25 (fallback policy on unmatched paths), 1.29 (axum's default body limit) and the cookie defaults in 3.4/3.6. One live request each against the real Sonarr would settle them.
